# Data Bender v1.4.7: platform, memory, audio transport, and control hardware

## Scope and confidence

This report analyzes the supplied `Data_Bender_v1_4_7.bin` and `DB-back.png`. Addresses below are virtual flash addresses for the image loaded at `0x08000000`; subtract that base to obtain the file offset. Function names are analyst assignments based on instructions and comparison with official libDaisy source. They are not recovered debug symbols. The narrow emulation described below executes initialization routines with explicitly documented peripheral/library stubs; it is not a full emulation of a physical module.

**Confirmed from the image:** a conventional flash-resident ARM Thumb application; STM32H7 peripheral addresses; libDaisy-style initialization; a 96-frame, stereo-interleaved callback; 24-bit SAI audio; twelve ADC controls; seven buttons; five external digital inputs including Clock; selectable codec initialization for three Daisy hardware families.

**Confirmed discrepancy:** the application initializes DSP objects with `96028.0f`, but the linked audio initialization requests **48,000 Hz**, not 96,000 Hz. This is supported by actual instruction execution, not only by looking up a numeric enum in a newer library. The physical rate predicted for a standard 16 MHz Daisy crystal is approximately **48,014.323 stereo frames/second**. It has not been measured on an actual Data Bender.

## Board identification

The supplied image shows a green motherboard marked `Data Bender`, `Rev1`, and `(C) Qu-Bit Electronix 2019`, with the characteristic yellow/gold Electro-Smith Daisy Seed daughterboard mounted across its upper region. The Qu-Bit official FAQ explicitly identifies the yellow board on the back of its modules as a Daisy Seed, and its Data Bender product information identifies the module as built on the Daisy platform.

The photo is sufficient for recognizing the platform, but not for confidently reading every IC marking or reconstructing all analog resistor/capacitor values. The apparent original Seed board is consistent with the AK4556 audio codec path. The firmware also supports later Daisy Seed 1.1 / WM8731 and Seed2DFM / PCM3060 hardware; the mere presence of these branches does not establish which codec is on the pictured physical board.

The binary establishes the STM32H7 architecture and libDaisy environment independently of the photo. The familiar Daisy Seed hardware identifies the likely MCU as STM32H750; the image alone does not distinguish all instruction-compatible STM32H7 silicon variants.

The arithmetic ratio `7,202,100 / 96,028 = 75.0` is exact, but it **does not establish a per-channel allocation or recording duration**. The buffer initializer at `0x08004a6c` halves its incoming count, and the main engine stores a separate pair of large addresses. These may describe different internal buffers. The custom DSP/buffer analysis must resolve the ownership and channel layout before deriving capacity; the platform analysis deliberately leaves this open.

`nondefault_vectors.csv` maps implemented vector entries against the official STM32H750 device header. A linked handler does not prove the associated peripheral is enabled or exposed as a module feature; generic library UART/SPI handlers are present too.

The binary uses the STM32H7 memory regions expected for a Seed: DTCM stack at `0x20000000`, AXI SRAM at `0x24000000`, DMA-visible SRAM at `0x30000000`, backup SRAM at `0x38800000`, memory-mapped external QSPI at `0x90000000`, and SDRAM at `0xc0000000`. `System::ConfigureMpu` at `0x080096e4` configures the first 32 KiB of DMA SRAM as noncached, the 64 MiB SDRAM region as cached/bufferable, and backup SRAM as noncached.

The initial LED DMA storage occupies `0x30000000 .. 0x30000108`. Audio transmit and receive storage begin at `0x30000108` and `0x30002108`; these are the two 8 KiB static arrays from libDaisy's audio transport, with unused capacity for another stereo SAI path. These are transport buffers, not the long sample memory.

## Audio transport and the sample-rate discrepancy

### What the application initializes

At `0x0800387e`, main loads the IEEE-754 float at `0x08003b48`, which is exactly `96028.0f`. This value is passed into the custom buffer/effect initialization. Hardware control smoothing initialization likewise uses `96028.0f` at `0x08005820` and `0x08005b58`.

At `0x080057ae`, hardware initialization loads `0x60`, stores it as the requested block size, and calls the recognized `DaisySeed::SetAudioBlockSize` wrapper at `0x08005c28`. Thus the requested transport block size is **96 stereo frames**.

Main loads callback address `0x080032fd` at `0x08003d1a` and calls `DaisySeed::StartAudio` at `0x08005c18`. The selected overload is the **interleaved** callback variant: `AudioHandle::Start` at `0x08006f58` stores the callback in the `interleaved_callback_` slot and clears the noninterleaved callback slot.

Equivalent callback signature:

```cpp
void callback(float* inputInterleaved,
              float* outputInterleaved,
              size_t scalarSampleCount);
// scalarSampleCount = 192 for 96 stereo frames: L0,R0,L1,R1,...
```

The internal audio conversion routine at `0x08006414` handles conversion between 24-bit signed codec samples and floating-point data. The initialized input postgain reciprocal and output compensation are both 1.0. The firmware DSP therefore works with conventional normalized float audio at this transport boundary.

### What the SAI initialization actually requests

`DaisySeed::ConfigureAudio` at `0x08005cd8` constructs a SAI configuration whose sample-rate field is integer 3 and bit-depth field is integer 1. The rate table used by **this binary's own** getter at `0x08019ed4` is:

| Rate field | Returned rate |
|---:|---:|
| 0 | 8,000 Hz |
| 1 | 16,000 Hz |
| 2 | 32,000 Hz |
| 3 | 48,000 Hz |
| 4 | 96,000 Hz |

The audio configuration literal at `0x08019c80` is four words equivalent to `{48, 3, 1.0f, 1.0f}`. The initial 48-frame block is later changed to 96 frames; there is no accompanying rate change in the recovered call path.

More decisively, `SaiHandle::Impl::Init` at `0x08008d3c` reads the rate field at config offset `0x10`. Its jump table at `0x08008da2` routes value 3 to `0x08008e86`, which stores the literal **48,000** into both HAL SAI handles' `AudioFrequency` fields. This eliminates uncertainty about whether enum 3 might have meant 96 kHz in a firmware-specific fork.

The normal original-Seed path configures:

- SAI1 block A: master transmit.
- SAI1 block B: synchronous slave receive.
- 24-bit sample data in two 32-bit slots, yielding a 64-bit stereo frame.
- MSB-justified protocol.
- MCLK on PE2, frame sync on PE4, serial clock on PE5, block A data on PE6, block B data on PE3.
- AK4556 codec reset on PB11.

### Clock/divider evidence

Actual instruction execution of `System::ConfigureClocks` at `0x08009550`, with low-level oscillator calls stubbed, captured these PLL3 values:

```text
M = 6
N = 295
P = 16
Q = 4
R = 32
FRACN = 0
```

The firmware's RCC code also contains the 16,000,000 Hz HSE constant, e.g. `0x08010130`, `0x08010400`, and `0x080119a8`. For a standard 16 MHz crystal, the SAI PLL3_P kernel clock is:

```text
16,000,000 × 295 / 6 / 16 = 49,166,666.667 Hz
```

Executing the firmware's `HAL_SAI_Init` at `0x08011a68` with that kernel frequency yields **MCKDIV = 4**. The captured block-A register values include `CR1 = 0x004002c0`, `FRCR = 0x00031f3f`, and `SLOTR = 0xffff0180` before the stream is enabled. With the configured 256× MCLK relationship, the predicted frame rate is:

```text
49,166,666.667 / 4 / 256 = 48,014.322917 Hz
```

A 96-frame callback therefore takes approximately 1.9994 ms of audio, or approximately 500.149 callbacks per second. The audio getter reports the nominal 48,000 Hz; the DSP's fixed 96,028 Hz design constant is separate.

This is a meaningful finding for a Rack recreation. The manufacturer publicly describes Data Bender as 96 kHz, and the DSP constants preserve that assumption, while this supplied binary's initialization requests 48 kHz. Do not silently collapse these into one number or assume that 7,202,100 samples necessarily mean 75 physical seconds in this build. A hardware recording or clock measurement would settle the physical behavior; the current result is strong binary evidence for the described initialization discrepancy.

No additional SAI initialization callsite was found: `DaisySeed::ConfigureAudio` calls `SaiHandle::Init` at `0x08005d48`; the wrapper calls its implementation at `0x0800934c`. The rate-setting wrapper is not present among the linked AudioHandle/Seed wrappers. The reset path selects internal-flash operation and initializes clocks, making retained bootloader clock state an unlikely explanation under the ordinary load path.

### Reproduction

`emulate_audio_config.py` performs four narrow checks:

1. Executes the actual `DaisySeed::ConfigureAudio`, recording the SAI and audio configurations at their call boundaries.
2. Executes actual `SaiHandle::Impl::Init`, recording both HAL handle configurations.
3. Executes actual `HAL_SAI_InitProtocol`, recording slot and frame setup.
4. Executes actual HAL divider arithmetic with an explicitly injected nominal kernel clock; independently records actual PLL configuration arguments.

The script names every stub and writes `audio_config_emulation.json`. It does not flash hardware, run the entire firmware, or claim a measured sample rate.

### Normalization and input conditioning

`AnalogControl::Process` at `0x08007078` reads a uint16 ADC value and divides by 65,536. The knob setup uses no inversion, flip, or offset. Its normalized target is therefore `raw / 65536`.

CV initialization at `0x0800700c` uses scale 2, offset 0.5, invert true, and flip false. Its normalized target is:

```text
CV = -2 × (raw/65536 - 0.5) = 1 - raw/32768
```

This confirms the normalized bipolar convention. It does not, by itself, prove the external voltage range; that requires the analog front end or a documented voltage specification.

Both paths use a one-pole update `value += coefficient * (target - value)`. The initial coefficient is clamped from `1 / (0.002 × (96028/96) × 0.5)`, approximately 0.999708. Time CV is explicitly overridden to coefficient 0.1 at `0x08005bb0`. Because the physical callback rate may differ from the fixed design rate, reproducing the coefficient verbatim at a new host rate would change its time behavior.

All five GateIn initializations enable inversion. `GateIn::Trig` at `0x080070e4` computes `state = !GPIO_Read()`, preserves the previous state, and returns a rising edge. This is consistent with the inverting transistor gate-input front end documented by libDaisy; do not apply that hardware inversion to the Rack voltage a second time. Buttons use inverted pull-up inputs and an eight-bit debounce history in the recognized `Switch::Debounce` routine at `0x0800713c`.

### LED interface

Hardware initialization uses I2C1 on D11/PB8 (SCL) and D12/PB9 (SDA), two addresses `0x40` and `0x41`, and 65-byte PWM register streams. This matches a pair of 16-channel PCA9685-style LED drivers. The seven RGB logical objects have these channel assignments:

| LED | Hardware object offset | RGB channels |
|---|---:|---|
| Shift | `+0x578` | 0, 1, 2 |
| Clock | `+0x590` | 3, 4, 5 |
| Mode | `+0x5a8` | 6, 7, 8 |
| Bend | `+0x5c0` | 9, 10, 11 |
| Break | `+0x5d8` | 12, 13, 14 |
| Corrupt | `+0x5f0` | 16, 17, 18 |
| Freeze | `+0x608` | 19, 20, 21 |

Notice that RGB object order differs from button order. Confusing these would produce plausible but incorrect panel feedback in a port.

## Codec revisions and output-polarity compensation

`DaisySeed::CheckBoardVersion` at `0x08005c6c` checks pulled-up GPIO inputs PD3 and PD4. PD3 low selects Seed 1.1 / WM8731; PD4 low selects Seed2DFM / PCM3060; otherwise the original AK4556 path is selected. These branches structurally match official libDaisy code.

Main separately samples PD4 and stores its inverted value at `0x24000410`. After the application DSP processes an audio block, `0x08003732 .. 0x08003750` conditionally negates **every right-channel output sample** when that flag is set. This is board-specific compensation for the Seed2DFM path and should not be blindly copied as universal stereo behavior in Rack.

The PCM3060 initialization branch also sets PB11 low to disable codec de-emphasis, as in the official libDaisy board configuration. That hardware control is separate from application DSP low-pass, DC, and Corrupt processing. A release note mentioning a high-pass-filter fix cannot be assigned to one specific block without comparison against an earlier firmware or other direct evidence.

## Recognized library layer and reuse boundaries

`function_labels.json` names the confidently matched hardware/runtime functions. The matching libDaisy code is especially useful for understanding the ABI, control normalization, debounce behavior, DMA conversion, and codec revisions. It is unnecessary to port HAL, GPIO, DMA, SDRAM initialization, or PCB-specific codec polarity behavior into Rack.

For the software recreation, preserve the public control semantics and the custom buffer/effect algorithms, supply normalized audio and CV from Rack, and derive time-dependent coefficients from the actual processing sample rate. Treat faithful reproduction of this build's rate mismatch as an explicit compatibility decision that requires hardware validation, rather than an unexamined consequence of copying constants.
