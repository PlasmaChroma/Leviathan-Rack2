# Vessel active-use performance investigation — October 9, 2026

## Outcome

No additional production DSP optimization was retained. The experiments preserved
the tested audio/energy fingerprints, but did not demonstrate a repeatable broad
CPU benefit. Production processing was restored to the previously validated
modal fusion/SSE2 implementation.

The useful additions from this pass are the connected-expander benchmark mode
and this record of the unsuccessful or inconclusive approaches. Do not repeat
these changes on the assumption that fewer source-level operations necessarily
mean a faster callback.

## Starting point

Baseline revision: `4e063cda49283c81378bc7e042ba6da6a67fec75`.

The prior pass already combined modal state updates, finite-state checks and
stereo pickup calculation, with two-mode double-precision SSE2 processing and
the original summation order. It measured approximately 4.6–4.8% lower callback
time for default-quality crystal/Wood rubbing. That optimization remains in
place. See [the performance log](vessel-performance.md#active-contact-modal-fusion-and-sse2-2026-10-08).

This investigation targeted further savings during active rubbing, rather than
passive ringing tails. Sample rates, solver tolerances, analytic friction,
double precision and control timing were to remain unchanged.

## Experiments

| Candidate | What was explored | Decision |
| --- | --- | --- |
| Contact-loop fusion | Compute free modal motion, tangential contact velocity and tangential admittance in one loop, preserving scalar reduction order. | Removed: mixed gains and regressions. |
| Prepared friction descriptor | Validate the unchanged mallet once at configuration and reuse that validation for rubbing-only solves. Preserve all changing-input checks and the uniqueness check. | Removed: no reliable broad gain. |
| Linked control reads | Skip six fallback parameter reads/clamps that a valid V.Tune message immediately replaces. Retain sample-rate control handling and parameter writes. | Removed: inconclusive callback timings. |
| Stereo decimator | Inspect the filtering implementation for duplicate work and SIMD opportunities. | Already uses symmetric taps, mirrored history and two-channel SSE2; no new filter implemented. |
| Conditional parameter writes | Inspect whether skipping unchanged V.Tune-to-Vessel writes would avoid costly setter work. | Not implemented: Rack setters are plain float stores; comparisons and branches could cost more. |
| Cached reciprocals | Consider replacing repeated divisions with multiplication by cached inverses. | Not implemented in this exact-output pass because it changes rounding. |

Contact fusion was measured alone and with descriptor caching. A further
candidate removed contact fusion while retaining caching and the control-read
change. The expander-read experiment also had a before/after pair with the
engine candidate held constant, isolating the control-read change.

The prepared-friction experiment did not change the coupled strike/rub solver
to use the cache. It was not a comprehensive optimization of every contact path.

## Measurement setup

- Native Windows, Intel Core i9-9900K, MSYS2 MinGW GCC 16.1.0, installed Rack 2 Pro runtime.
- Compiler options: `-O3 -march=nehalem -fno-fast-math -fno-unsafe-math-optimizations`.
- Harness: `tools/vessel/benchmark_active_module.cpp`, measuring complete headless `Vessel::process()` calls with debug timing disabled.
- 48 kHz host, C4, 0.2 rev/s Rub speed and 2.5 N pressure.
- Sixteen fixtures: crystal/Wood and metal/Suede; 96/192 kHz internal quality settings; zero/33 Hz binaural separation; continuous rubbing with or without a strike every 250 ms.
- Each fixture has three fresh instances, each with one simulated second of warmup and one simulated second of timed processing.
- Main comparisons used three serial executable runs and reversed ordering. Summaries use the median of the three run means.
- No builds or tests ran concurrently with the timing passes.

A second series pinned the launcher and inherited child processes to logical
CPU 2, affinity mask `4`. The launcher's affinity was restored afterward. This
did not stabilize the results enough to support a small optimization claim.

The harness excludes Rack scheduling, the GUI and the audio driver. It measures
average callback cost, not a guaranteed worst-case deadline or a live Rack CPU
meter reading. The run labels named `final` identify an experimental candidate,
not code that was ultimately retained.

## Results and interpretation

The unpinned contact-only comparison ranged from approximately **10% slower to
5% faster** across fixture medians. Contact plus caching ranged from **2.5%
slower to 7.6% faster**. Affinity-constrained comparisons still showed mixed
signs and some differences exceeding 20%.

These ranges are screening observations, not achieved speedups. Timing noise,
scheduling, frequency variation and code-layout effects were not separated well
enough to attribute the small gains to the proposed optimizations. Neither a
few favorable cases nor an overall average justified promoting the candidates.

Every compared audio/energy fingerprint matched its baseline. Fingerprints are
generated in separate untimed traces spanning Rub release, strike re-entry and
pitch modulation. This supports equivalence for the exercised trajectories; it
does not establish equivalence for all possible patches or fault conditions.

Candidate-only regression tests were drafted but removed with the rejected DSP.
They are not claimed as completed candidate validation. After restoring the
production implementation, the native Windows `plugin.dll` build and complete
`test-vessel` suite passed. The retained benchmark target also compiled.

## Retained benchmark capability

`--expander` supplies a static valid V.Tune message to measure Vessel's linked
callback. It excludes V.Tune's own callback and Rack's message-flip scheduling.

Build in the MINGW64 environment:

```sh
make -j10 build/tools/vessel_benchmark_active_module
PATH="/c/Program Files/VCV/Rack2Pro:$PATH" \
  build/tools/vessel_benchmark_active_module.exe --expander
```

Omit `--expander` for standalone Vessel. Keep the Rack runtime directory first
on PATH so its matching runtime DLLs are loaded.

## Next direction

Obtain a stable sampled profile of active crystal/Wood rubbing before making
more small source-level rearrangements. Separate time spent in modal work,
friction/contact solving, filtering and Rack control handling. Measure single
and binaural operation separately, and include both steady rubbing and strikes
during rubbing.

Once a dominant remaining cost is established, benchmark an isolated change
against the saved baseline and check its broader cases before adoption. The
existing SIMD improvement remains useful; this pass simply did not establish
another safe, repeatable gain.
