## Audio and background dependencies

- `src/codec.cpp` has a Temporal Deck WAV decoder, but it reads a whole file into a byte vector, allocates separate channel vectors, clamps float samples to `[-1,1]`, does not retain cue markers, and does not support float64 WAV. Its API is unsuitable for Chimera's full-capacity, amplitude-preserving canonical import. Reuse its low-level format lessons where useful; implement a bounded, streaming Chimera WAV reader/writer into a prepared store.
- The installed Rack SDK includes `speex/speex_resampler.h`; `dsp/resampler.hpp` wraps it. `SampleRateConverter` construction, `setQuality`, and `setRates` call `refreshState()` and can allocate/free. Prepare and retire converter state off audio. `tests/chimera_speex_link_probe.cpp` links through the native SDK's `-lRack` and runs against the Rack Pro runtime. At quality 5, input SRC latency was 40 host frames at 8/44.1 kHz, 80 at 96 kHz, 160 at 192 kHz, and 640 at 768 kHz. The Speex API exposes input/output latency; still verify the complete adapter with impulses in Phase 6.
- `src/SpscLatestSnapshot.hpp` is a one-producer/one-consumer latest-value exchange, not a lossless command queue. `src/Iris.cpp` demonstrates worker completion and onSave, but its private per-module thread and image-oriented payload are not appropriate for full Reel I/O. Bifurx has a plugin-scoped render service whose shutdown is explicit; Chimera needs a separate bounded I/O service with at most two global workers.
- The live 48 kHz core should own active pages; one immutable lease protects worker reads. One service/control dispatcher owns the service-to-audio SPSC producer. Audio owns the completion/retirement SPSC producer. UI and semantic callers submit into the same non-RT dispatcher. UI and semantic status cannot both consume one SPSC snapshot directly. Retirement and lease release must happen before off-audio destruction. `destroy()` drains workers after modules/jobs have stopped accepting commands.
- At 768 kHz, 16 host frames map to one core frame. Encoding a jack's connection and edge in one record gives at most `13*16=208` jack records per core frame, below the 256-event cap. With measured maximum quality-5 input delay of 640 host frames, the steady delayed history holds `13*640=8320` records under all-jacks-changing-every-frame stress. `tests/chimera_phase0_capacity_spec.cpp` measures an 8,333-record transient peak when the next host frame is enqueued before the oldest frame is consumed. A proposed 16,384-entry jack history covers that ordering and scheduling margin; Phase 6 must stress it with actual bridge timing. Continuous control history is separate. The same test proves that active plus prepared full stores fit within 256 MiB raw audio, while a leased retired third full store cannot be admitted.

## Rack save and duplication contract

- Installed SDK `engine::Module::onSave(const SaveEvent&)` returns `void`; patch storage calls cannot occur in the constructor or audio callback. The adjacent Rack source's `Engine::prepareSave()` calls `onSave` while holding a shared engine lock, before `patch::Manager::saveAutosave()` builds JSON and the archive. `Engine::moduleToJson()` also holds a shared engine lock. Chimera must not attempt a lock upgrade from either hook. The inspected source invokes save preparation on patch-manager destruction too; do not throw from the hook as an unverified universal abort strategy.
- `patch::Manager::saveAutosave()` can serialize through `dataToJson()` outside a preceding `onSave` preparation. Its temporary `patch.json` rename does not make external module audio current. `dataToJson()` must identify an actually durable audio cut or explicitly mark missing/unsaved audio; it may not attach current markers to an old audio file.
- Single-module `ModuleWidget::cloneAction()` calls `prepareSaveModule()`, serializes JSON, and copies source patch storage to a new module ID before adding the clone. In contrast, `RackWidget::cloneSelectionAction()` uses `selectionToJson()` and `RackWidget_pasteJson()`; it does not call the save hook or copy each source module's patch storage. A same-process Chimera duplicate from an unsaved recording therefore needs a plugin-owned immutable checkpoint/content-addressed reference that the clone can resolve and copy into its own mutable store. A bare JSON preset/clipboard on a different machine remains explicitly missing-audio unless assets travel separately.
- `tests/chimera_rack_patch_save_spec.cpp` drives the installed Rack Pro patch manager without the GUI, using a small file-backed bundle prototype. It archives and extracts a real Save and alternate-path Save, checks autosave before `onSave`, and verifies stopped/bypassed and shutdown save preparation. A failure before the first complete bundle archives a missing-audio diagnostic. A failure after new audio is written but before manifest publication still creates an archive; its JSON references the prior complete manifest and audio, with `saveFailure` set. The void hook does not cancel Rack's save. Whole-patch atomic cancellation is not available through this tested hook; the module owns coherent fallback assets and visible error state. An unreferenced orphan audio file may be archived after failure and must be pruned later.
- `tests/chimera_rack_save_contract_spec.cpp` runs against the installed Rack DLL. It confirms that Engine `prepareSaveModule()` and `prepareSave()` invoke `onSave`, while ordinary `dataToJson()` leaves live state unsaved and can report only the earlier durable revision. It does not exercise the GUI clone paths or the patch archive writer. The isolated test includes internal SDK headers to instantiate a stack Engine; production Chimera code should continue to use the public `rack.hpp` API.
- The patch-manager fixture additionally models the two source-backed clone sequences with Rack Engine APIs. Single-module duplication prepares and copies source patch storage; selection duplication only serializes JSON, so it needs a plugin-owned immutable checkpoint reference to recover unsaved audio in the same process. The fixture copies that checkpoint into independent clone storage and verifies a clone edit cannot mutate the source cache. An absent cache on another machine is a missing-asset condition. Actual Rack GUI commands and portable real-module reload remain Phase 7 end-to-end tests.
