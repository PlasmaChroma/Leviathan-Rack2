# Chimera versus Morphagene MG204: controls and I/O audit

## Implementation follow-up

The original audit below records the **pre-alignment** implementation. The
subsequent firmware-alignment change implements:

- The clock quantizer's upper-bin rule, exact Gene Size ROM table, and ordered
  cube-then-span arithmetic.
- All three Vari-Speed ROM target mappings and their distinct index masks;
  forward-only reaches 4x. New modules default to the recovered 1x bin, and
  the rate quantity displays/accepts the new stepped curve.
- Per-Gene original/swapped stereo crossmix, discrete chord-rate selection,
  conditional LCG consumption, and the exact default third chord ratio.
- Extracted Morph launch/density values instead of rational substitutes. The
  existing fractional-phase scheduler still governs lifecycle/transitions;
  this is not a reconstruction of every firmware scheduler state.

Parameter/jack IDs and stored knob values are unchanged. Existing patches now
use the corrected rate curve, Gene durations and Morph behavior; there is no
legacy-sound toggle. Rack voltage conventions, CV front-end and host smoothing
remain in place. Envelope state, gain normalization, adaptive readers, and the
conditional recording filter remain deferred until their controlling firmware
state can be mapped reliably into the engine. No hardware-equivalence claim is
made for those paths or for the full random sequence across a patch.

Runtime tables are generated by `tools/generate_chimera_firmware_tables.py`;
`tests/chimera_firmware_alignment_spec.cpp` compares the live helpers with the
audited reference and fixed offline examples, including a rendered stereo test.

Native validation: firmware-alignment tests with normal and fast-math flags,
phase-1 tests and vectors with normal/fast flags, Gene Size, Morph, grain,
S.O.S., Slice, Clock, and Rack-linked module regressions passed. Windows
`plugin.dll` linked successfully. The broader `test-fast` run stopped at two
Sibyl fixture failures: "P5 complete companion expressive-composition fixture
compiles" and "P6 combined source compiles". Those sources were not modified.
No installation, staging, or commit was performed.

## Original audit

Reviewed 2026-09-27 against the current working tree. Firmware directory is
`firmware/Morphagene` (the requested `Moraphgene` spelling does not exist).
No module implementation was changed, staged, or committed.

The current audited REPORT.md supersedes several claims in the older handoffs.
Its reconstructed components are instruction transcriptions, not an entire
firmware emulator or hardware recording oracle. Conclusions below distinguish
confirmed algorithm differences from unverified hardware-interface details.

## Most consequential differences

### 1. Clocked Gene Size chooses a lower duration bin

Firmware keeps the current upper bin once the preliminary duration crosses
the next lower boundary. Chimera starts at half the splice and descends until
its candidate is below the preliminary duration. These are different musical
quantizers, not a Rack adaptation.

Native comparison using a 480,000-sample splice:

| Preliminary duration / splice | Firmware samples | Chimera samples |
|---|---:|---:|
| 0.7 | 480000 | 480000 |
| 0.6 | 319999.65625 | 240000 |
| 0.4 | 239999.75 | 160000 |
| 0.3 | 159999.671875 | 120000 |
| 0.2 | 119999.75 | 80000 |
| 0.1 | 59999.8125 | 40000 |

This changes Gene lifetime, retrigger density, clock-driven source motion, and
associated boundary timing. Chimera also uses exact 2/3 in its descending loop,
where firmware repeatedly uses the stored approximate coefficient.

Evidence: `src/ChimeraGeneSize.hpp:36`; firmware `REPORT.md:176`;
`reconstruction/audited_components.hpp` clockQuantize; firmware store at
0x0802acd6 and quantizer at 0x0802ab6c..0x0802abd8.

The unclocked law is substantially aligned: whole-splice mode at ADC <=199,
long-splice folding above 576,000 samples, exponential table cubing, and an
eight-sample minimum. Lesser differences remain: Chimera regenerates the table
using float arithmetic, multiplies span*x*x*x rather than (x*x)*x*span, rounds
duration to integer frames, and updates on every changed mapped code instead
of the recovered greater-than-32-code firmware deadband. These have much lower
priority than the incorrect clock bin, but deadband affects modulation response.

### 2. Vari-Speed is a different control law

Chimera uses a continuous power curve chosen to put +1x at knob 5/6 and -1x
at 1/6. Firmware uses quantized ROM rate targets, including explicit stop
entries. Modes 0 and 1 clear different low bits of the table index; this is
absent from Chimera. Forward-only mode has a particularly clear range mismatch:
firmware reaches 4x before pitch modulation, Chimera reaches 2x.

The following compares the same normalized *post-calibration coordinate*;
it does not assert identical physical panel angles or hardware CV calibration.

| Coordinate | Firmware classic | Chimera classic | Firmware forward | Chimera forward |
|---|---:|---:|---:|---:|
| 0 | -2 | -2 | 0 | 0 |
| 0.25 | -0.5 | -0.611512 | 0.153007 | 0.070838 |
| 0.5 | 0 | 0 | 0.5 | 0.376445 |
| 0.75 | 0.529732 | 0.611512 | 1.633915 | 1 |
| 5/6 | 0.840896 | 1 | 2.413009 | 1.288992 |
| 1 | 2 | 2 | 4 | 2 |

Chimera mode 0 combines knob and attenuverted CV before rate mapping. Modes
1/2 multiply the base curve by 2^(attenuverter*volts), with pitch clamped to
±8 octaves and final rate clamped to ±32. The option names agree with the
firmware, but that does not establish equivalence of the complete rate path.
Firmware upstream calibration, holdoffs, clock multiplier, and pitch processing
must be considered separately from the verified table target.

Evidence: `src/ChimeraProfile.hpp:65`, `src/ChimeraCore.hpp:77`;
firmware `REPORT.md:383`, rateTarget transcription and exact rate CSVs.

### 3. Upper Morph does stereo balance instead of stereo crossmix

Firmware stores a per-Gene coefficient p and renders:

    Lout = (1-p)*L + p*R
    Rout = p*L + (1-p)*R

Above Morph 0.5, the probability of selecting a random p rises approximately
as 2*M-1; otherwise p is zero. On success p spans the full 0..1 range.

Chimera instead draws a bipolar pan whose depth grows from zero and applies
separate equal-power channel gains. It never transfers the left sample into
the right channel or vice versa. Therefore firmware leaves identical mono
channels unchanged by this operation, while Chimera moves that mono signal
across the stereo field. A left-only source can cross into the right output in
firmware, but this Chimera operation alone cannot do that.

This is a substantial audible difference, not just a different random seed.
Evidence: `src/ChimeraProfile.hpp:224`, `src/ChimeraGrains.hpp:447` and :273;
firmware `REPORT.md:252`, launch at 0x0802842a..0x08028490 and render at
0x08028c36..0x08028c5a.

### 4. Upper Morph selects chord pitches differently

Firmware chooses a rate index approximately as trunc((M-0.6)*9.999*U),
selecting base, mcr1, mcr2, or mcr3. This progressively admits further ratios:
at M=0.65 the index remains zero, so this operation produces no chord pitch.

Chimera uses probability (M-0.6)/0.4 to activate a chord on slots 1..3;
the slot fixes which ratio is used, and slot 0 always stays at base pitch.
At M=0.65, eligible slots can already use any of their three assigned ratios.
This changes both onset distribution and which voices can change pitch.

Firmware uses an LCG and two or three launch draws depending on stereo
selection; Chimera uses Xorshift32 and two unconditional draws. Matching only
the generator would not reproduce a complete patch's sequence because the
firmware has other RNG consumers. Default mcr3 also differs slightly: firmware
0x3faaaaaa versus Chimera's double 4/3.

Evidence: same Chimera onset/launch functions; firmware `REPORT.md:279`.
A native 100,000-launch transcription probe at M=.65 selected base every time.

### 5. Morph overlap loudness, grain windows, and playback timbre differ

Chimera divides the voice sum by max(1,sum of weights). Firmware derives a
gain-table index from envelope-state sum, then smooths the table target with
0.01 per frame. These are different gain dynamics as overlap changes.

Chimera uses cosine-shaped edges: normally 96 samples, or max(96,20% of
duration) for smooth Genes, capped to fit the Gene. It blends to a flat window
near seamless density. Firmware includes half-duration envelope quantities,
a 24,000-sample cap, and separate 250-sample/0.004 branches affected by gnsm
and overlap. The full firmware envelope is not reconstructed, so those facts
support a mismatch but not a complete replacement window specification.

Chimera's default reader is unity-gain Catmull-Rom cubic; its optional quality
mode uses a bandlimited reader. Firmware switches at block level between a
four-tap quadratic with raw DC gain two and a linear reader with doubled
envelope scaling, depending on envelope-state sum relative to two. The
kernel shapes differ even after accounting for gain conventions. This affects
high-frequency response, transients, and aliasing across Morph overlap.

Evidence: `src/ChimeraGrains.hpp:314`, :471;
`src/ChimeraProfile.hpp:149`; firmware `REPORT.md:216`, :301, :383.
Improved resampling can be an intentional quality option, but is not required
by Rack and should not be confused with firmware-equivalent playback.

### 6. S.O.S. source routing matches; recorded feedback coloration does not

All 4,096 S.O.S. target codes matched exactly in the native arithmetic probe.
The endpoint margins, complementary live/playback mix, and 0.001-per-frame
smoothing coefficient are represented. Startup seeding and floating-point
execution are not claimed bit-identical.

Both implementations use the S.O.S. mix for recording with inop=0 and live
input with inop=1. But firmware conditionally applies this record-only filter
after source selection:

    y[n] = 0.7*x[n] - 0.7*x[n-1] + 0.997*y[n-1]

Chimera writes the selected source without that stage. Its DC blockers are
instead on the live input and monitor output, with pole approximately
0.999345716 and no 0.7 scale. They are not equivalent in placement or response.
Thus repeated overdubs can differ in level and bass/DC behavior even with the
same S.O.S. setting. Firmware also records to int16 planes; Chimera retains
floating-point reel samples.

The filter's firmware enable condition is an equality between two splice state
values. Its applicability to every current/new-splice transition remains
unresolved: do not simply apply this filter to all recording as a 'fix'.

Evidence: `src/ChimeraSlice.hpp:279`, :359, :413, DcBlocker at :496;
firmware `REPORT.md:341`, routing/filter at 0x08028e7a..0x08028ef0.

## Exact implemented I/O and remaining firmware uncertainty

All formulas below describe Chimera. k is the normalized knob; a is its
attenuverter; v is CV in volts. Normalized sums are clamped to [0,1].
Hardware volts-to-ADC calibration is outside this firmware update, so the
following voltage scales cannot be certified or rejected from the table
reconstruction alone.

| Control / jack | Chimera behavior | Comparison status |
|---|---|---|
| S.O.S. knob/CV | Unpatched: k. Patched: k*clamp(v/8,0,1), then recovered target shaping. Zero or negative CV forces live-only. | DSP target and complementary mix match; hardware CV frontend unverified. |
| Gene Size + amount | k+a*v/8, 2 ms one-pole, mapped to whole/finite Gene law. | Broad unclocked law matches; clock-bin mismatch confirmed. |
| Vari-Speed + amount | Classic coordinate 2*k-1+a*v/4. Other modes use exponential pitch CV on the knob base rate. | Rate-law mismatch confirmed; full hardware voltage calibration unverified. |
| Morph CV | k+v/5; 2 ms one-pole before stage mapping; additional 0.01/frame continuous smoothing for randomization. | Stage bins match; rational launch values approximate ROM; upper behavior differs. |
| Slide + amount | k+a*v/8; targets fraction of selected splice length minus one; source motion limited to 64 samples/frame and moves active voices/tails too. | Exact hardware motion/update law not established by current audit. |
| Organize CV | k+v/5; selects one of N splice bins with 10%-of-bin hysteresis; changes normally commit at primary boundary. | Boundary vs immediate policy agrees with omod description; exact bin/hysteresis semantics unverified. |
| SHIFT | Jack rising edge advances requested splice modulo count; button acts on release. | Precise firmware event ordering unverified. |
| SPLICE | Jack rising edge/button release adds marker at writer while recording current splice, otherwise playback position; append has deferred handling. | Complete firmware splice/write event trace needed. |

| CLOCK | Hybrid switches to stretch at Morph launch factor <=1/2; explicit shift/stretch modes available. | Audio inputs | Left defaults zero; unpatched right copies left. Gain choices approximately -3/0/+6/+12 dB. Normalize 5 V to 1; input DC block. | Firmware traced live path includes 1.5 scaling/clipping; exact codec/calibration and jack normalization need more tracing. |

## Smaller precision and control-response differences

- Morph's stage calculation matches the recovered 22 stages, but Chimera
  replaces ROM launch factors with exact rational scheduling. Eleven active
  launch entries differ from rounded rational fractions. Usually much smaller
  than the upper-Morph semantic differences, but not bit-exact timing.
- Firmware ADC averaging windows are 16/16/64/64/4/64 conversions for
  S.O.S./Morph/Organize/Vari-Speed/Slide/Gene Size. Chimera's smoothing and
  slew limits do not reproduce those windows. ADC cadence is unresolved, so
  no exact millisecond comparison is justified.
- Tail crossfades, host-rate conversion, asynchronous storage, and voltage
  conventions are reasonable port engineering. Audible changes in the
  rate law, crossmix, chord chooser, or quantizer are separate design choices.
- Firmware memory capacity is 2^23 stereo frames versus Chimera's 8,352,000
  frames (174 seconds at 48 kHz). Physical capacity is not proof of firmware
  maximum usable record length, so this alone is not an established missing feature.

## Suggested order for fidelity work

1. Correct the clock duration quantizer against the audited reference.
2. Decide whether Vari-Speed should adopt recovered target tables, including
   forward-only 4x, and preserve existing patch behavior if needed.
3. Implement recovered Morph stereo crossmix and discrete pitch selection as
   a coherent behavior change, rather than merely replacing the PRNG.
4. Trace remaining envelope state, then address overlap gain and kernels together.
5. Resolve the record-filter condition before changing overdub DSP.
6. Audit CV/EOSG outputs, Slide motion, Organize bins, PM depth, and clock/play/
   record event ordering before describing those interfaces as exact matches.
